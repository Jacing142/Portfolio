GUARDRAILS

Production systems fail in boring ways

Someone uploads the wrong file. An API times out. An edge case appears on day one. I design for those paths as carefully as the happy one.

This list is not theoretical. Reviewing another company's agents in production, I found guardrails living only in the system prompt, which is a weak default rather than a control, some agents with no prompt at all, customer data reaching the model unmasked, and nothing logged, so nobody could say what any of it had cost.

What if it gets something wrong?

Outputs are scored against defined checks before release. Below the threshold nothing ships, it goes to a person with the full context.

What if it breaks?

Validation at intake, retries and fallbacks. Failed runs are surfaced, never swallowed.

What if someone tries to trick it?

Anything the system reads from outside, an email, a document, an uploaded file, is treated as data rather than instructions. Content and commands stay separated, and a system that ingests untrusted input never holds permissions it does not need for that job.

What about our data?

Sensitive information is filtered before it reaches a model. Least-privilege access, and nothing leaves your systems.

What is it allowed to do?

Every action a system can take is on a list, and the list is enforced in code rather than in the prompt. Read access is separated from write access. Anything irreversible, sending to a customer, changing a record, moving money, needs either a person or a rule that cannot be talked out of it.

Can we turn it off?

Nothing runs that your team cannot stop, change or switch off.

What if you disappear?

Everything is documented as it is built, because one person is a single point of failure and pretending otherwise helps nobody. Your team is trained on it, the monitoring is yours, and nothing depends on me being reachable.

What happens when the model changes?

Models get deprecated and updated whether you are ready or not. The test cases your system was accepted against are kept, so a swap is a decision with evidence behind it rather than a surprise in production.

Can we explain it to an auditor?

Escalations carry the reasoning that triggered them, and outputs trace back to the criteria that produced them.

BEFORE IT SHIPS, AND WHILE IT RUNS

How I know it works

Systems are tested against real cases in a sandbox and must clear agreed quality thresholds before they go near production. A system nobody has measured isn't a system, it's a demo.

What it did, why, and what it cost

Every run is logged: what came in, what the system did with it, where it stopped. When something goes wrong you can see which step failed rather than reconstructing it from the output. Cost is capped per run and tracked against that cap, so spend is a number you set rather than a surprise at the end of the month.

Outcome
What the system passes is right over 99% of the time.
Used by
The operations team, and the manufacturers downstream of them.
